# DAL_PDU documentation and simulation

## Build bootloader-ready firmware

Run these commands from the PDU repository root. They require GNU Make, Python 3,
AVR-GCC (on `PATH` or in the Microchip Studio 7 toolchain), and the sibling
`../Bootloader/AVR_Booyloader/AVRBootLoader/tools/boot_host.py` packager.
Set `AVR_TOOLCHAIN` to the AVR toolchain `bin` directory and `AVR_DFP` to an
ATmega device pack directory if they are installed elsewhere.

```powershell
make original  # Refresh Git build identity; compile release/DAL_PDU.elf and .hex
make signed    # Build original, then create release/DAL_PDU_signed.hex
make clean     # Remove the files produced by these targets
```

`make` defaults to `signed`. The original HEX is linked from flash address zero
and ends before the metadata page. The signed target invokes the AVR bootloader
packager to append the metadata page with image CRC and numeric build ID. This
package is **CRC-checked, not cryptographically signed**. Upload the signed HEX
with `xbld_client`; use the original HEX only where no bootloader metadata is
needed.

The last signed build ID is stored in `signed_build_id.txt`. Each successful
`make signed` increments it by one, even when the source has not changed. To set
the next ID manually, edit that file to one less than the desired ID (for
example, write `41` to make the next signed image ID `42`). A packaging failure
does not advance the file. The Git hash reported by the firmware's `version`
command is a separate build identity. To use a different packager path, run
`make signed BOOT_HOST=path/to/boot_host.py`.

This folder holds the DAL_PDU design documentation and its board simulation. The folders are:

| Folder | Contents |
|---|---|
| `doc\` | MkDocs site with the firmware and software design documents. Pages are in `doc\docs\`. |
| `sim\` | Labcenter Proteus simulation of the board. |
| `firmware\` | Atmel Studio project for the firmware. |
| `tests\` | Host unit tests. |

## Get the repository

The firmware uses two third-party projects as git submodules: FreeMODBUS and `printf`. A plain clone
does not download them, so the firmware will not build. Clone with the submodules in one step.

Requires Git for Windows 2.x. Run these in PowerShell or Git Bash.

### Clone a new copy, with the submodules

```powershell
git clone --recurse-submodules <repo-url> PDU
cd PDU
git submodule status
```

`git submodule status` should list two lines, each with a commit hash and a path:

- `firmware/DAL_PDU/DAL_PDU/src/dev/M4_MiddleWare/ThirdParty/freemodbus`
- `firmware/DAL_PDU/DAL_PDU/src/dev/M4_MiddleWare/ThirdParty/printf`

### Update an existing clone

If you already cloned without `--recurse-submodules`, or the submodule folders are empty, run this from
the `PDU` folder:

```powershell
git pull
git submodule update --init --recursive
git submodule status
```

If `git submodule status` shows a `-` before a hash, the submodule is not initialized. Run
`git submodule init`, then the update command again.

If a submodule folder is still empty after the update, clear its stale state, then fetch it again:

```powershell
git submodule deinit -f firmware/DAL_PDU/DAL_PDU/src/dev/M4_MiddleWare/ThirdParty/freemodbus
git submodule deinit -f firmware/DAL_PDU/DAL_PDU/src/dev/M4_MiddleWare/ThirdParty/printf
git submodule update --init --recursive
```

A `+` before a hash means the checked-out commit differs from the one the repository records. Run
`git submodule update --init --recursive` to return it to the recorded commit.

### What is not in the repository

- The `ref\` folder holds reference copies of other projects. It is not part of this repository, and the
  firmware does not need it. Get those projects from their own repositories if you need them.
- `firmware\DAL_PDU\DAL_PDU\src\dev\M1_Sys\Versionuild_id.h` is generated by `tools\gen_build_id.py`.
  It is tracked in git, and it changes with each build. Run the script before a build from a fresh clone
  (the test Makefile runs it for you).
- `release\` and the Studio `Debug\` and `Release\` folders are build output.

## Prerequisites

- Python 3.8 or newer, with `pip`.
- MkDocs, installed once:

  ```powershell
  pip install mkdocs
  ```

- Internet access in the browser when viewing pages. Mermaid diagrams are loaded from a CDN.

## Run the documentation server

Change into the documentation folder first:

```powershell
cd PDU\doc
mkdocs serve
```

Open http://127.0.0.1:8000/ in a browser. The server reloads automatically when you save a file in
`doc\docs\` or change `doc\mkdocs.yml`.

### Use a different port

Pass the address and port with `-a`:

```powershell
cd PDU\doc
mkdocs serve -a 127.0.0.1:8080
```

To reach the site from other machines on the network, bind to all interfaces:

```powershell
mkdocs serve -a 0.0.0.0:8080
```

To make the port permanent for this project, add it to `doc\mkdocs.yml`:

```yaml
dev_addr: 127.0.0.1:8080
```

If `mkdocs` is not on your PATH, run it through Python instead, for example
`python -m mkdocs serve -a 127.0.0.1:8080`.

## Build a static site

To produce HTML files without a server, for example to share or archive:

```powershell
cd PDU\doc
mkdocs build --strict -d site
```

- `--strict` makes broken internal links and anchors fail the build. Run it before committing changes.
- `-d site` writes the output to `PDU\doc\site`. Choose another folder if you prefer.

The `site\` folder is generated output and should not be edited by hand.

## Add or change a page

1. Create or edit a Markdown file in `doc\docs\`.
2. Add it to the `nav:` section of `doc\mkdocs.yml` so it appears in the sidebar.
3. Link to other pages with relative paths, for example `[Scheduler design](scheduler_design.md)`. For a
   section, add the anchor, for example `scheduler_design.md#6-coalescing`. Headings keep their section
   numbers in anchors.
4. Run `mkdocs build --strict` from `PDU\doc` to check the links.

## Simulation (`sim\`)

`sim\` holds the Labcenter Proteus simulation of the DAL_PDU board.

| Item | Purpose |
|---|---|
| `New Project.pdsprj` | The Proteus project. It is a zip archive, not plain text. Open it in Proteus. |
| `New Project.pdsprj.<machine>.Admin.workspace` | Per-machine window layout saved by Proteus. Not needed to run the simulation. |
| `Project Backups\` | Timestamped copies and an autosave made by Proteus. Restore one by opening it in Proteus. |

### What the project runs

The ATmega128 model in the project loads the firmware by reference:

```
PROGRAM = ..\firmware\DAL_PDU\DAL_PDU\Debug\DAL_PDU.elf
```

The clock is set to 16 MHz, matching `F_CPU` in the firmware. The path is relative to the project file, so
keep `sim\` next to `firmware\`. The project was saved with file version 830.

### Run the simulation

1. Build the firmware first, so the ELF is current:
   - Open `firmware\DAL_PDU\DAL_PDU.atsln` in Atmel Studio 7 and build the **Debug** configuration, or
   - Run `make` in `firmware\DAL_PDU\DAL_PDU\Debug`. That Makefile is generated by Studio and uses its toolchain paths.
2. Open `sim\New Project.pdsprj` in Proteus.
3. Right-click the ATmega128 and check that its program file points to `Debug\DAL_PDU.elf`. If it does not, set it to that file.
4. Start the simulation with the play button.
5. Open a Virtual Terminal, set 9600 baud, 8N1, and connect it to the console UART. Type `help` and press Enter.

Rebuild the ELF after each firmware change. Proteus does not rebuild it for you.

### Limits of the simulation

- The `Debug\DAL_PDU.elf` in the tree dates from before the most recent scheduler and command changes.
  Rebuild before relying on it.
- Only the MCU program reference and clock were checked. Confirm that the schematic contains the parts
  the firmware drives, such as the TPS55287, PAC1934, 24C04, and the external TPL5010 watchdog. A missing part
  will read as a dead bus or a stuck pin, not as a firmware fault.
- A simulation does not measure real timing, UART signal integrity, or the RS485 bus. Use it for logic and
  command checks, then confirm on the board.

## Troubleshooting

- **`mkdocs` is not recognized.** Use `python -m mkdocs ...`, or add the Python `Scripts` folder to PATH.
- **Port already in use.** Choose another port with `-a`, or stop the process using the port.
- **Diagrams show as code blocks.** The browser cannot reach `cdn.jsdelivr.net`. Check the network or proxy.
- **Build fails with a warning about an anchor.** Check the heading text in the target page; anchors include
  the section number.
- **`mkdocs serve` says no config file.** You are not in `PDU\doc`. Run `cd PDU\doc` first, or pass
  `-f PDU\doc\mkdocs.yml`.
