# Open issues

Historical entries below describe earlier command behavior. As of 2026-10-16, `mode retry`
has been removed; `mode normal` performs the regulator/limit health check before clearing
those ERROR causes. A confirmed eFuse fault raises WARNING in NORMAL, remains latched in
all modes, and does not trigger a software VOUT/TRANS shutdown or block TRANS enable.
`fault clear` removes the recorded latch. TPS55287 feedback behavior has also changed:
firmware now selects internal feedback (`0x04 = 0x03`) and accepts 800–20000 mV.
OI-32 below records the earlier external-feedback decision; the populated R22/R30
network makes bench verification of the new setting necessary.

This page lists the work still open against the requirements, use cases, and user stories in
[Software requirements](software_requirements.md) and [Use cases, user stories & commands](use_cases_commands.md).
Status is as of 2026-10-05, checked against the firmware. The per-requirement status tables are in
[Software requirements §7](software_requirements.md#7-implementation-status).

Priority is set by safety impact first, then by how much other work depends on the item.

- **High**: affects protection, failsafe behavior, or a use case the OBC relies on.
- **Medium**: needed for the requirement to be fully met, but the system is still safe without it.
- **Low**: documentation, verification, or cleanup.

| OI-31 | **Resolved 2026-10-15.** The TPS55287 (U5) is behind the TRANS eFuse, which stays off at boot by design, so it could not answer the startup self-test, which unconditionally latched ERROR on every boot and then blocked `trans on`/`tps55287 on` from ever succeeding (`AppMode_Get() != APP_MODE_ERROR` gates `AppPower_SetTrans(true)`). The one-second rail monitor made it worse: it kept polling the TPS55287 even while TRANS was correctly off at idle, re-latching ERROR on the first pass. The self-test no longer probes the TPS55287; the regulator is instead checked on demand (`AppPower_EnsureRegulatorOn`) the first time TRANS is enabled, from `trans on`, `tps55287 set`/`on`, or the equivalent Modbus writes (coil `00001`, holding `40001`). The rail monitor now only polls while TRANS is on. `mode retry` had the same deadlock one level up: it probed the chip directly (`BSP_TPS55287_Detect`) without powering TRANS, so `regulator_ok` was always false while TRANS was off, and since `AppMode_Retry` only clears a cause when both the regulator and the limits check out, a persisted **limit** ERROR from before a reset (EEPROM-backed, unrelated to the regulator) could never be cleared either as long as TRANS stayed off. `mode retry` now calls `AppPower_ProbeRegulator()`, which powers TRANS just long enough to probe (skipping the probe entirely if the eFuse fault is latched) and restores it to how it was found either way. | `PWR-011`, `PROT-050` | `UC-1`, `UC-8` | None open. Re-arming the TPS55287's feedback/voltage registers after a power-cycle is now done too (OI-32). See [Mode state machine](mode_state_machine.md). |
| OI-32 | **Resolved 2026-10-15.** This board wires an external feedback divider (R22 = 102 kΩ, R30 = 11.3 kΩ to GND; ratio ≈ 0.0997, confirmed on hardware), but the TPS55287 resets to internal feedback (register `0x04` = `0x03`) every time its `EN`/UVLO drops, and nothing ever wrote that register — so after any TRANS power-cycle (the normal idle-off case, every time, after OI-31), the chip was running the wrong ratio. The driver rejected the external case outright (`TPS55287_SetVoltageMv`/`GetVoltageMv` returned false whenever the FB bit was set), so this was invisible rather than dangerous as long as nothing wrote register `0x04` to `0x80` manually; if it had been written, the chip would have used the external ratio's math nowhere in the firmware, risking the wrong output voltage (see the TPS55287 safety review discussion, ~21 V from a 12 V command in the worst case). `TPS55287_SetVoltageMv`/`GetVoltageMv` now compute against either ratio, selected by the FB bit already read from the chip. `AppPower_SetTrans(true)`/`AppPower_EnsureRegulatorOn()` now write register `0x04` to `0x80` and read it back to confirm, right after the presence probe, every time TRANS powers on — so the chip is always in external feedback before `tps55287 set`/`on` or the equivalent Modbus write can run. | `PWR-010`, `PWR-013`, assumption `A-4` | `UC-1` | Confirm the 0.0997 ratio and the ~12 V range against a bench measurement, per `A-4`; the resistor values are not yet independently verified beyond what was reported. |
| OI-33 | **Decided 2026-10-15.** `BSP_Power_SetTrans(true)` and `BSP_TPS55287_SetEnabled(true)` no longer check the live PC4/PC0 pins before enabling; only a *latched* fault still refuses (`s_latch` in `AppPower_SetTrans`), which is what `SRS-PWR-015` actually requires ("shall not enable ... while a fault is latched"). `SRS-PWR-015` and `SRS-PROT-023` are otherwise unchanged and still enforced: a real, ongoing fault is still caught, latched, and shuts TRANS/VOUT back off by the unchanged 6 ms `AppPower_Update` poll, within one cycle of the enable attempt. The only effect is a narrow race window: a fault that is live but not yet latched no longer makes that single `trans on`/`tps55287 on` call itself fail; it succeeds momentarily and is then caught and reversed by the next poll. Requested to stop a live-but-unlatched fault from refusing re-enable during bench bring-up. | `PWR-015`, `PROT-023` | `UC-4` | None open. If the race window itself (a brief, true enable before the next 6 ms poll) is unacceptable, the removed pre-checks would need to come back. |
| OI-34 | **Decided 2026-10-15.** MANUAL now outranks ERROR in `AppMode_Get()` (checked first), and `AppMode_RequestManual()` no longer refuses while `s_regulator_error` is set. Previously, a stuck regulator/limit ERROR (for example from `mode retry` genuinely failing, not just the OI-31 case) left no way out at all: `mode manual` was refused for the same reason `trans on` was, so the operator had no path to take manual control and work around a stuck automatic retry. Once MANUAL is requested, `AppPower_SetTrans`'s `AppMode_Get() != APP_MODE_ERROR` gate passes, so `trans on`/`tps55287 on`/the equivalent Modbus writes work directly, regardless of the regulator/limit cause underneath — consistent with MANUAL already disabling automatic regulator monitoring (`AppMode_RegulatorMonitored()`). The eFuse latch gate (`s_latch`, OI-33) is untouched and still refuses regardless of mode. `mode retry` still clears the underlying regulator/limit cause but does not by itself exit MANUAL; `mode normal` is still refused until that cause is actually clear. | `PWR-011`, `PWR-015`, `PROT-050` | `UC-8` | None open. See [Mode state machine](mode_state_machine.md) and software requirements §3. |

## Dependencies

- OI-02 (mode state machine) is needed by OI-01, OI-03, OI-04, OI-05, and OI-10.
- OI-11 (configuration record) is needed by OI-12 and OI-16. OI-04 and OI-05 use it for their limits, which are done.
- OI-16 (bootloader) owns the bank header that OI-15 needs.
- OI-07 and OI-14 were decided together on 2026-10-06. OI-28 fixes the fault inputs that OI-14 lists.
