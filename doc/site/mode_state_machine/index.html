Mode state machine

This page describes the operating mode as implemented in M0_App/app_mode.c (2026-10-05). The mode is one of four: NORMAL, MANUAL, WARNING, and ERROR. The earlier four-state model (Standby, Running, ProtectedShutdown, SafeFault) is gone.

1. Modes

Mode Value Entered when Outputs (VOUT, TRANS) Commands Regulator monitored
NORMAL 0 No error, and no manual request Allowed. Limits act. All Yes
MANUAL 1 Requested by command, from NORMAL, WARNING, or ERROR (revised 2026-10-15: outranks ERROR once requested) Allowed, including trans on/tps55287 on, regardless of a regulator/limit cause underneath. Limits log only. All No
WARNING 2 The PAC1934 is unreadable, an I2C timeout is active, the VOUT setpoint readback mismatches, or Modbus link loss (SRS-COM-045) Allowed. Link loss by itself does not turn outputs off. Limits log only. All Yes
ERROR 3 The regulator (U5) does not respond when TRANS is enabled, or it faults or stops responding while TRANS is on; a limit trips in NORMAL; or an eFuse fault (PC4 for 12V TRANS, PC0 for 12V_MCU) reads continuously active for 50 ms (revised 2026-10-16, was WARNING — see SRS-PROT-020) Both off, unless MANUAL has since been requested All No

The mode is derived on each call to AppMode_Get(). The first matching rule wins:

  1. MANUAL, if a manual request is active (revised 2026-10-15: checked before ERROR, so a manual request always wins — see OI-34).
  2. ERROR, if the regulator error flag, the limit error flag, or a latched eFuse fault is set (revised 2026-10-16: the eFuse latch moved here from WARNING — see OI-35).
  3. WARNING, if the PAC1934 is unreadable, an I2C timeout is active, the setpoint readback mismatches, or Modbus link loss is active.
  4. NORMAL otherwise.

Every mode accepts all commands and responds. ERROR's causes (regulator, limit, and the eFuse latch) and MANUAL are independent flags: requesting MANUAL does not clear any of them, it only changes which one AppMode_Get() reports and which gates (like AppPower_SetTrans's ERROR check, and the eFuse auto-shutdown in AppPower_ShutdownOnFault) are satisfied. A healthy mode normal request clears regulator/limit causes; only fault clear removes an eFuse latch. Leaving MANUAL still requires an explicit mode normal request after clearing the latch. The regulator is not watched automatically in either MANUAL or ERROR.

2. Transitions

From To Trigger Actions

Startup WARNING PAC1934 not detected None
Startup ERROR Limit ERROR flag stored from an earlier trip Both outputs off until a healthy mode normal request
Startup NORMAL No error None
NORMAL or WARNING ERROR Regulator status fault (SCP, OCP, or OVP), or regulator stops responding Both outputs off
NORMAL ERROR Over-temperature or overcurrent limit exceeded for the required samples (PROT-021, PROT-022) Both outputs off. WARNING event logged.
MANUAL, WARNING, or ERROR (no change) Over-temperature or overcurrent limit exceeded WARNING event logged. Outputs unchanged.
NORMAL or WARNING ERROR PC4 (while TRANS is on) or PC0 reads continuously active for 50 ms (revised 2026-10-16, was WARNING) Latched fault: outputs off (unless in MANUAL — see below), latch in EEPROM
NORMAL or WARNING WARNING PAC1934 unreadable None
NORMAL or WARNING WARNING No valid Modbus request for the configured timeout, after at least one was seen (SRS-COM-045) None. Outputs are not turned off by this.
WARNING NORMAL Cause clears (PAC1934 readable, or a new valid Modbus request arrives) None
NORMAL, WARNING, or ERROR MANUAL mode manual, or Modbus holding register 40030 = 1 (revised 2026-10-15: reachable from ERROR too) None. The regulator/limit/eFuse-latch cause, if any, is untouched.
MANUAL or ERROR NORMAL or WARNING mode normal, or Modbus holding register 40030 = 0 Checks regulator and limits; clears those causes only when healthy. Refused while an eFuse fault is latched.
ERROR (eFuse latch) NORMAL or WARNING fault clear, refused while the live pin is still active Clears only the eFuse cause.

A confirmed eFuse fault behaves like any other ERROR cause for mode purposes (MANUAL still outranks it), but only fault clear removes its latch.

Requests to enter NORMAL while a regulator/limit health check fails or an eFuse fault remains latched are refused. The console prints MODE refused: error, and Modbus returns an exception. Requests to enter MANUAL are never refused for this reason (revised 2026-10-15, OI-34).

3. Regulator monitor

The one-second rail monitor (AppPowerMonitor_Update) reads the TPS55287 status register while the mode is NORMAL or WARNING and TRANS is on. The TPS55287 (U5) sits behind the TRANS eFuse and is unpowered whenever TRANS is off, so the monitor does not poll it then — polling an unpowered chip would otherwise read back as a failure and set ERROR for no reason. Any SCP, OCP, or OVP flag, or a failed read while TRANS is on, sets the ERROR flag. The flags are cleared by the read, so the monitor acts on the value it has just read. ERROR is cleared only by a healthy normal-mode request.

The same reasoning applies to enabling TRANS: AppPower_SetTrans(true) and AppPower_EnsureRegulatorOn() (used by tps55287 set/on and the equivalent Modbus writes) probe the TPS55287 right after powering TRANS on, and set the ERROR flag (turning TRANS back off) if it does not answer. Right after that probe, they also write register 0x04 to external feedback (0x80) and read it back to confirm, since the chip resets to internal feedback every time its EN/UVLO drops — which happens on every TRANS power-cycle. This board wires an external divider (R22/R30, ratio ≈ 0.0997) rather than using the chip's internal ratio, so a failed readback there sets ERROR the same way a failed presence probe does.

mode normal probes the regulator through AppPower_ProbeRegulator() when a regulator or limit ERROR is set, so it also works from a cold boot with TRANS off: it powers TRANS on just long enough to check (unless the eFuse fault is latched, in which case it refuses without touching TRANS), then restores TRANS to whatever it was before, whatever the result. That lets mode normal clear a persisted limit ERROR too, not only a regulator ERROR — AppMode_Retry requires both causes to be clear before it drops either one, so without this probe a stale limit ERROR left over from before a reset could never be cleared while TRANS was off.

4. Outputs

  • ERROR: AppPower_Update turns VOUT off, then TRANS off, on every 6 ms pass while TRANS is on — unless MANUAL has been requested since, in which case outputs stay under manual control. TRANS cannot be enabled from ERROR itself (only from MANUAL, which outranks it).
  • Link timeout (SRS-COM-045, revised 2026-10-15): if no Modbus request has arrived for the configured timeout (default 5 s) after the first one, this raises the link WARNING cause in mode get. It no longer turns VOUT or TRANS off by itself, and is not persisted (plain RAM state, cleared the instant a new valid Modbus request arrives). Previously this turned outputs off without changing the mode; that was reversed because in practice it was tripping during console-only bench use with no Modbus traffic at all, not an actual lost link in the field — see OI-03.
  • Latched eFuse fault (revised 2026-10-16, SRS-PROT-020): PC4 (while TRANS is on) or PC0 must read continuously active for 50 ms before it is treated as real — a brief read, for example from inrush when TRANS switches on, resets the timer and never latches. Once confirmed, it is ERROR, not WARNING, and stays latched until fault clear, regardless of mode — enabling is refused by the latched record, checked in AppPower_SetTrans. While in MANUAL, a confirmed fault is still latched and reported (fault get, and mode get's latch=), but AppPower_ShutdownOnFault no longer forces outputs off for it, matching every other ERROR cause once MANUAL has been requested. The live PC4/PC0 pins themselves are no longer checked at the moment of enabling (decided 2026-10-15): a fault that is live but not yet confirmed does not refuse a trans on/tps55287 on attempt by itself. The 6 ms AppPower_Update poll still reads the live pins every pass and, once the 50 ms debounce confirms a real fault, latches it and shuts TRANS back off (outside MANUAL) — so a fault that is still present gets caught and the output disabled within about 50 ms regardless; this only removes a synchronous pre-check that duplicated that poll on the same tick as the enable attempt.
  • Over-temperature and overcurrent (PROT-021, PROT-022): checked every second in every mode. Temperature needs two consecutive samples at or above the limit. Each current needs three consecutive samples above it.
  • Every trip is logged once as a WARNING event in the 24C04, whatever the mode. A trip is logged again only after the value has returned under the limit.
  • In NORMAL, the trip also turns VOUT and then TRANS off and sets the limit ERROR.
  • In MANUAL, WARNING, and ERROR, the trip only logs. Outputs are not changed.
  • Limit ERROR end: mode normal clears it once the regulator responds and every limit is back in range. The flag is stored in internal EEPROM, so the ERROR survives a reset until that request succeeds. The health check does not leave an output on.

5. Self-test

The startup self-test runs once in APP_Initialize, before the scheduler starts. The TPS55287 (U5) sits behind the TRANS eFuse, which stays off at boot by design, so it cannot be probed here. It is not part of the startup self-test: it is checked on demand instead, the first time TRANS is enabled (see section 3).

Device Result Effect
U10 PAC1934 Missing WARNING
U14 24C04 Missing Recorded only. Shown by mode as eeprom=1.

The self-test is synchronous, so it is never visible as a mode.

6. LED indication

The heartbeat LED (PA3) shows the mode. Patterns are in app_heartbeat.c.

Mode Pattern ON / OFF (ms)
NORMAL Slow heartbeat 1000 / 1000 (configurable with the led command and Modbus 40020–40023)
MANUAL Medium blink 200 / 800
WARNING Double flash 100 / 100, then 100 / 1000
ERROR Rapid blink 50 / 50

The heartbeat enable (Modbus coil 00010, led command) applies to the NORMAL pattern only. Faults always show.

7. Console and Modbus

Interface Operation
mode or mode get Prints the mode, then CAUSES regulator=0 pac1934=0 eeprom=0 latch=0 limit=0 setpoint=0 bus=0 link=0. A 1 means that cause is active. regulator, limit, and latch are ERROR causes; pac1934, setpoint, bus, and link are WARNING causes (eeprom only records itself, per section 5). latch moved from WARNING to ERROR 2026-10-16 (SRS-PROT-020).
mode normal Checks the regulator and limits when an ERROR cause is set, clears healthy causes, then requests NORMAL. Refused if the check fails or an eFuse fault is latched.
mode manual Requests MANUAL. Never refused for being in ERROR (revised 2026-10-15, OI-34) — the regulator/limit/latch cause, if any, is untouched underneath.
limit, limit temp <tenths C>, limit vout <mA>, limit trans <mA> Shows or sets the limits. Stored in internal EEPROM.
config, config set address, config set baud, config set timeout, config_reset confirm Shows or sets the Modbus address, baud, and communications timeout, or restores all settings to the defaults. See Command reference.
event get Lists the events in the 24C04 ring, with the clock time.
Modbus input 30022 Mode value: 0 NORMAL, 1 MANUAL, 2 WARNING, 3 ERROR.
Modbus holding 40030 Read: mode value. Write 0 requests NORMAL, 1 requests MANUAL.
Modbus holding 40031–40033 Limits: temperature in tenths of a degree C (signed), VOUT in mA, +5_TRANS in mA. A refused write returns an exception.

8. Known limits

  • The limit defaults are 85.0 °C for two samples, and 1000 mA for three samples on VOUT and on +5_TRANS. They need bench confirmation. The values are in the ATmega128A internal EEPROM, as SRS-CFG-060 now requires (OI-11).
  • A limit ERROR is kept across a reset in internal EEPROM. It clears on a healthy mode normal request, once the limits are back in range.
  • The Modbus limit registers 40031–40033 are in the implemented map. The design draft has no equivalent (OI-14).
  • The startup self-test checks that the PAC1934 and 24C04 acknowledge. It does not check their configuration, and it no longer includes the TPS55287 (see section 5).
  • The regulator presence check now runs on demand, the first time TRANS is enabled after boot or after being turned off, rather than at startup. Nothing currently re-arms the TPS55287's own registers (feedback mode, voltage reference) after TRANS has been power-cycled; only its presence is re-checked.
  • The link timeout raises the link WARNING cause and no longer turns outputs off by itself (revised 2026-10-15; see the open question below, now resolved).
  • The eFuse fault debounce is fixed at 50 ms (EFUSE_FAULT_DEBOUNCE_MS in app_power.c), not yet bench-tuned against the actual inrush duration on this board.
  • Only the regulator fault flags are monitored. Other regulator faults (for example thermal) are not yet read.
  • An I2C timeout from the TPS55287 sets ERROR while the regulator is monitored (NORMAL or WARNING) and TRANS is on, as the regulator rule requires (OI-26). In MANUAL it sets only the WARNING cause (bus=1 in mode), and the mode stays MANUAL. A timeout from any other device sets WARNING until a transaction completes. A NACK from an absent device is not a fault.
  • The bootloader is not implemented, so there is no bootloader mode.

9. Open question

  • Link timeout (Q7 follow-up) — resolved 2026-10-15. Decided the other way from the original 2026-10-05 call: link loss now sets WARNING and no longer turns outputs off by itself. See section 4 and OI-03.
