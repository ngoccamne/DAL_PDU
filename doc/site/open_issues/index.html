Open issues

This page lists the work still open against the requirements, use cases, and user stories in Software requirements and Use cases, user stories & commands. Status is as of 2026-10-05, checked against the firmware. The per-requirement status tables are in Software requirements §7.

Priority is set by safety impact first, then by how much other work depends on the item.

  • High: affects protection, failsafe behavior, or a use case the OBC relies on.
  • Medium: needed for the requirement to be fully met, but the system is still safe without it.
  • Low: documentation, verification, or cleanup.

High priority

ID Issue Requirements Use cases / stories Next step
OI-01 Resolved 2026-10-05. Fault latch and clear. A fault that switches TRANS off is latched in the ATmega128A internal EEPROM and survives reset. PROT-023, PROT-020 UC-4; "fault latches" story Cleared by Modbus coil 00003 or fault clear. trans on is refused while latched. See Modbus RTU implementation and Current command reference.
OI-02 Resolved 2026-10-05. Mode model: NORMAL, MANUAL, WARNING, and ERROR. The mode is derived from the regulator flag, the limit error, the manual request, the PAC1934 status, and the fault latch. PWR-011, PWR-015, PROT-050, MON-033 UC-8 Revise PROT-050 in the SRS, since the retry command now exits ERROR. Bootloader mode is still open under OI-16. See Mode state machine.
OI-03 Resolved 2026-10-05, revised 2026-10-15. Modbus link loss (default 5 s without a request) is now a WARNING cause (mode get's link=) and no longer turns outputs off or latches anything by itself; see SRS-COM-045. Previously it turned VOUT and the transducer branch off while leaving the mode unchanged — decided to drop that, since the only thing that was tripping it in practice was console-only bench use with no Modbus traffic, not a real lost-link condition in the field. COM-045, WDT-080 "fail safe on lost Modbus" story Watchdog client coverage for Modbus is still open under OI-08. If a real field deployment needs the output shutdown back, it would need to be reintroduced deliberately, not inferred from this entry.
OI-04 Resolved 2026-10-05 with defaults. Overcurrent in NORMAL mode: 1000 mA on VOUT (decided 2026-10-06) or +5_TRANS for three samples turns outputs off, enters ERROR, and logs a WARNING event. Limits are set with limit and stored in internal EEPROM. PROT-022, CFG-060 UC-4 Confirm the default on the bench. The limits are on Modbus 40031–40033. The map is aligned under OI-14.
OI-05 Resolved 2026-10-05 with defaults. Over-temperature in NORMAL mode: 85.0 °C for two samples turns outputs off, enters ERROR, and logs a WARNING event. The threshold is set with limit temp and stored in internal EEPROM. PROT-021, CFG-060 UC-4 Confirm the default on the bench. The threshold is on Modbus 40031. The map is aligned under OI-14.
OI-06 Resolved 2026-10-06. The rail monitor checks the PAC1934 VOUT voltage against the commanded setpoint once a second, while TRANS and VOUT are on. Each judged sample must be within 5 % of the setpoint (at least 100 mV). Three judged samples out of tolerance flag a WARNING and log SETPOINT_MISMATCH. The first two checks after a change are not judged. PWR-014, COM-040 UC-1; "read back actual voltage" story None open. Confirm the tolerance and settling on the bench.
OI-31 Resolved 2026-10-15. The TPS55287 (U5) is behind the TRANS eFuse, which stays off at boot by design, so it could not answer the startup self-test, which unconditionally latched ERROR on every boot and then blocked trans on/tps55287 on from ever succeeding (AppMode_Get() != APP_MODE_ERROR gates AppPower_SetTrans(true)). The one-second rail monitor made it worse: it kept polling the TPS55287 even while TRANS was correctly off at idle, re-latching ERROR on the first pass. The self-test no longer probes the TPS55287; the regulator is instead checked on demand (AppPower_EnsureRegulatorOn) the first time TRANS is enabled, from trans on, tps55287 set/on, or the equivalent Modbus writes (coil 00001, holding 40001). The rail monitor now only polls while TRANS is on. mode retry had the same deadlock one level up: it probed the chip directly (BSP_TPS55287_Detect) without powering TRANS, so regulator_ok was always false while TRANS was off, and since AppMode_Retry only clears a cause when both the regulator and the limits check out, a persisted limit ERROR from before a reset (EEPROM-backed, unrelated to the regulator) could never be cleared either as long as TRANS stayed off. mode retry now calls AppPower_ProbeRegulator(), which powers TRANS just long enough to probe (skipping the probe entirely if the eFuse fault is latched) and restores it to how it was found either way. PWR-011, PROT-050 UC-1, UC-8 None open. Re-arming the TPS55287's feedback/voltage registers after a power-cycle is now done too (OI-32). See Mode state machine.
OI-32 Resolved 2026-10-15. This board wires an external feedback divider (R22 = 102 kΩ, R30 = 11.3 kΩ to GND; ratio ≈ 0.0997, confirmed on hardware), but the TPS55287 resets to internal feedback (register 0x04 = 0x03) every time its EN/UVLO drops, and nothing ever wrote that register — so after any TRANS power-cycle (the normal idle-off case, every time, after OI-31), the chip was running the wrong ratio. The driver rejected the external case outright (TPS55287_SetVoltageMv/GetVoltageMv returned false whenever the FB bit was set), so this was invisible rather than dangerous as long as nothing wrote register 0x04 to 0x80 manually; if it had been written, the chip would have used the external ratio's math nowhere in the firmware, risking the wrong output voltage (see the TPS55287 safety review discussion, ~21 V from a 12 V command in the worst case). TPS55287_SetVoltageMv/GetVoltageMv now compute against either ratio, selected by the FB bit already read from the chip. AppPower_SetTrans(true)/AppPower_EnsureRegulatorOn() now write register 0x04 to 0x80 and read it back to confirm, right after the presence probe, every time TRANS powers on — so the chip is always in external feedback before tps55287 set/on or the equivalent Modbus write can run. PWR-010, PWR-013, assumption A-4 UC-1 Confirm the 0.0997 ratio and the ~12 V range against a bench measurement, per A-4; the resistor values are not yet independently verified beyond what was reported.
OI-33 Decided 2026-10-15. BSP_Power_SetTrans(true) and BSP_TPS55287_SetEnabled(true) no longer check the live PC4/PC0 pins before enabling; only a latched fault still refuses (s_latch in AppPower_SetTrans), which is what SRS-PWR-015 actually requires ("shall not enable ... while a fault is latched"). SRS-PWR-015 and SRS-PROT-023 are otherwise unchanged and still enforced: a real, ongoing fault is still caught, latched, and shuts TRANS/VOUT back off by the unchanged 6 ms AppPower_Update poll, within one cycle of the enable attempt. The only effect is a narrow race window: a fault that is live but not yet latched no longer makes that single trans on/tps55287 on call itself fail; it succeeds momentarily and is then caught and reversed by the next poll. Requested to stop a live-but-unlatched fault from refusing re-enable during bench bring-up. PWR-015, PROT-023 UC-4 None open. If the race window itself (a brief, true enable before the next 6 ms poll) is unacceptable, the removed pre-checks would need to come back.
OI-34 Decided 2026-10-15. MANUAL now outranks ERROR in AppMode_Get() (checked first), and AppMode_RequestManual() no longer refuses while s_regulator_error is set. Previously, a stuck regulator/limit ERROR (for example from mode retry genuinely failing, not just the OI-31 case) left no way out at all: mode manual was refused for the same reason trans on was, so the operator had no path to take manual control and work around a stuck automatic retry. Once MANUAL is requested, AppPower_SetTrans's AppMode_Get() != APP_MODE_ERROR gate passes, so trans on/tps55287 on/the equivalent Modbus writes work directly, regardless of the regulator/limit cause underneath — consistent with MANUAL already disabling automatic regulator monitoring (AppMode_RegulatorMonitored()). The eFuse latch gate (s_latch, OI-33) is untouched and still refuses regardless of mode. mode retry still clears the underlying regulator/limit cause but does not by itself exit MANUAL; mode normal is still refused until that cause is actually clear. PWR-011, PWR-015, PROT-050 UC-8 None open. See Mode state machine and software requirements §3.

Medium priority

ID Issue Requirements Use cases / stories Next step
OI-07 Resolved 2026-10-06. The commanded setpoint, the four rails' voltage and current, and the four rails' power are on Modbus 30023–30038, and in the telemetry command. Power is in 10 mW units. Board temperature is on 30021. COM-040, MON-030 UC-3; "read back current" story None open.
OI-08 Resolved 2026-10-05. Five clients now check in: console and heartbeat (200 ms), Modbus (200 ms, 5 ms task), and the rail monitor and temperature task (1500 ms, which covers their 1 s period). A client that stops is recorded in the boot record and the unit resets. WDT-080 UC-7 Confirm the timeouts against the TPL5010 window (OI-25).
OI-09 Resolved 2026-10-05. The reset flags are read first at startup. A watchdog fault is kept in a .noinit RAM note and written to the boot record at the next boot. The last 10 boots are kept in internal EEPROM. bootinfo shows the last boot, and bootinfo history lists the stored boots. The last boot is also on Modbus input registers 30032–30034. WDT-081 UC-7; "event log" story None open.
OI-10 Partly resolved 2026-10-06. Events are a 32-slot ring in the 24C04, stamped with the software clock (SRS-MON-034). Limit, I2C, setpoint, configuration, and clock events are logged. The OBC reads the newest event, or any event by sequence, over Modbus (40050, 30041–30047). eFuse faults, regulator faults, mode changes, link loss, and resets are not logged yet. MON-032, MON-034, WDT-081 UC-6; "event log" story Log the remaining events through AppEvent_Log. Log a boot event after EEPROM init, for WDT-081. Add a rate limit and a RAM queue for the EEPROM writes.
OI-11 Resolved 2026-10-05. Configuration is in internal EEPROM with a checksum, a version byte, and compiled defaults. The record holds the Modbus slave address, the baud code, and the communications timeout. The limits share the EEPROM. config, config set, and config_reset confirm set them, and a blank or damaged record falls back to the defaults. CFG-060, CFG-062, COM-041 UC-6 None open. Writes to internal EEPROM are not gated, by decision.
OI-12 Resolved 2026-10-05. The Modbus slave address and baud rate come from the configuration record. Set them with config set. They take effect at the next boot. COM-041 UC-6 None open.
OI-13 Resolved 2026-10-06. The firmware names are the reference. status and reset confirm are added. The design names STAT, FAULT?, FAULT CLR, LOG?, TEMP?, ILIM, and RESET are dropped, and the mapping is in Command reference. The design command table itself is not in the docs. COM-042, COM-043 UC-6; "technician console" story Restore the design table if a copy exists, so the superseded section has a source.
OI-14 Resolved 2026-10-06. The implemented Modbus map is the reference. The differences from the design draft and each decision are in Modbus RTU implementation. COM-040 UC-1, UC-2, UC-3 None open.
OI-15 Resolved 2026-10-06. The build identity is generated from git (tools/gen_build_id.py). version prints it, and Modbus 40107–40108 carry it. Release copies are named with the version and the build (tools/release.py). GEN-092 — Add the build ID to telemetry if the OBC needs it. The bank header comes with OI-16.
OI-16 Bootloader and dual-bank firmware update. Nothing is implemented: no image path, no CRC check, no bank switch, no confirm-or-rollback. BOOT-070 to BOOT-076, CFG-061 UC-5; "firmware update without bricking" story Treat as its own milestone. Start with the flash layout (BOOT-070) and the bank header (BOOT-071).
OI-17 Calibration of the output range. The TPS55287 limits come from the driver, not from a calibration. PWR-013, assumption A-4 UC-1 Measure the output across the range on the bench. Record the calibrated safe range, and set it as the limit.
OI-18 Scheduler worst-case timing. Task dispatch latency is not measured, and overruns are coalesced without a count. GEN-090, GEN-091 — Add a per-pass timing measurement and an overrun counter. See Scheduler design §9 (R2, R3, R4).

Low priority

ID Issue Requirements Use cases / stories Next step
OI-19 Debug UART exclusivity. Nothing keeps the debug UART inactive during PC104 operation. COM-005 — Decide how the debug port is disabled in flight configuration. Implement the interlock or document the procedure.
OI-20 Resolved 2026-10-06. SRS-COM-030 is defined: RS-485 idle noise is handled by T3.5 framing, the address check, and the CRC, as A-3 accepts the weak bias. COM-030 — Bench check of the Modbus noise handling.
OI-21 Resolved 2026-10-06. The RS-485 pins are PD2 (MCU RX), PD3 (MCU TX), and PD5 (DIR), confirmed on the board. SRS-COM-002 is updated to match. COM-002 — None open. The review schematic (rev 1.1.0) still shows PD4/PD5/PD6 and must be updated.
OI-22 Resolved 2026-10-06. The Studio project already sets the FreeMODBUS include paths (modbus\include, modbus\rtu) and the defines MB_ASCII_ENABLED=0 and MB_FUNC_OTHER_REP_SLAVEID_ENABLED=0 in both configurations. Those defines are needed: mbconfig.h enables both by default, and their code calls mbascii.c and mbfuncother.c, which are not in the project. The project's 69 sources compile and link for the ATmega128A with these settings. COM-040 (build) — Confirm a clean build in the Studio IDE.
OI-23 Temperature reference. The ADC reference is assumed to be 5.000 V, and the module is not calibrated. The review BOM also has C59 (AREF) at 12 pF, against 100 nF in the schematic. MON-031, PROT-021 UC-3 Measure the 5 V rail on the bench, and check the reading against a reference temperature. Fit C59 as the schematic shows, then adjust the AVcc constant if needed.
OI-24 Hardware-dependent checks. The firmware is verified only on the host and in Proteus. The board items are: PC104 RS-232 direction (IF-001), RS-485 polarity and timing, I2C rise times, and the Proteus model's peripherals. COM-001, COM-002, assumptions A-1 to A-5 — Run bench tests for each item. Confirm the Proteus model includes the TPS55287, PAC1934, 24C04, TC1047A, and TPL5010.
OI-25 Resolved 2026-10-05. The TPL5010 window is 10 s. The 1500 ms slow-client timeout and the 50 ms first check-in are both well inside it. WDT-080 UC-7 None open.
OI-26 Resolved 2026-10-05. A TPS55287 I2C timeout sets ERROR while the regulator is monitored (NORMAL or WARNING), as PROT-050 requires. In MANUAL it sets only the WARNING cause, and the operator decides. A timeout from any other device sets WARNING until a transaction completes. PROT-050, PWR-010 UC-8 None open.
OI-27 The TWI recovery does not free a slave that holds SDA low. The bus stays faulted until the device releases it. WDT-080 UC-7 Add a 9-clock bus clear on timeout if a device is seen holding the bus.
OI-28 Resolved 2026-10-06. PC4 is the 12V TRANS fault and PC0 the 12V_MCU fault. PC1 is not connected, and the firmware no longer reads it. The MCU-branch fault is latched, turns outputs off, and enters WARNING (PROT-020), and it is reported on 10002 and 30020 (PROT-024). The fault latch keeps its two bits, now PC4 and PC0. PROT-020, PROT-024, PWR-010 UC-4, UC-8 None open. Confirm the PC0 and PC4 levels on the board.
OI-29 Resolved 2026-10-06. Pins confirmed on the board: PC4 is the 12 V TRANS fault, PC0 is the 12 V_MCU fault, and the TPL5010 WAKE is PB5. The review had PAC1934 INT on PC4; it is on PE7. The firmware polls the PAC1934 and does not use PE7. PROT-020, WDT-080 UC-4, UC-7 Correct the review pin table: PAC1934 INT on PE7, PC0 and PC2 added. The review package is outside this repo.
OI-30 Resolved 2026-10-06. The console is the software UART on PE3/PE4. This is accepted for MCU-001, and no USART pair is used for it. COM-004 UC-6 P2 needs a defined pinout (CON-002) for bench use.

Dependencies

  • OI-02 (mode state machine) is needed by OI-01, OI-03, OI-04, OI-05, and OI-10.
  • OI-11 (configuration record) is needed by OI-12 and OI-16. OI-04 and OI-05 use it for their limits, which are done.
  • OI-16 (bootloader) owns the bank header that OI-15 needs.
  • OI-07 and OI-14 were decided together on 2026-10-06. OI-28 fixes the fault inputs that OI-14 lists.
